《饥馑的盛宴》序章：四幕选项与因果线
核对日期：2026-10-18
核对入口：当前仓库的实际界面、状态转移和结算代码；不把保留的旧玩法当作当前入口。

主线
能多做 → 谁分得收益、谁决定经营 → 做出来是否卖得出 → 消费、投资、出口怎样改变订单与代价 → 换条件再试。
这条线组织玩家的问题，不表示现实经济只能依次经历这些阶段，也不是必然危机的证明。

第一幕：更大的烤炉
1. 看原来的生产和分配：这车面包收款10枚，厨师拿5枚。
2. 换炉后这车收款15枚。玩家用＋/−决定给厨师多少，确认后可重新分配，或继续看扩张。
3. 当前可确认3—7枚。越界会触发人物台词并回到边界，非完整谈判模型；抱怨和老板反应含剧情设定。
4. 直接影响：这一幕的工资选择、角色反应、留下的钱，以及随后扩张设想中同一工资参数。
5. 扩张是预设动画：1组增长到2、4、8、16、32、64组。它示意购置、工资、投入和收款的先后，前提是货持续卖出、价格和每位厨师工资不变。
6. 15枚是销售收款，15减工资不是完整净利润；扩张钱堆也不是老板个人净财富。
7. 转场：进入第二幕后另起账本。第一幕工资选择保留为记录，但不带入面包店对决的资金、工资或设备。
对应代码：lib/trust-stage.js 的 bakery/bakery-upgrade/bakery-expansion；lib/bakery-expansion.js；lib/prologue-state.ts 的 EXPANSION_CONTINUE。

第二幕：面包店对决
三场分别提出三个问题：固定客流怎样多赚；需求变化时怎样安排；少发工资、多卖产品能否让本店资金净增更多。

共同可选操作
调低售价／调高售价：当天生效，价格范围1—5。
购置机器：付10枚，明天添普通炉；不附赠厨师。
升级新机：每台旧炉8枚，整店当天停炉安装；工资和老板生活费照付，可卖已有库存，明天按快炉能力生产。
招工：明天生效，从现有待业者招聘；不凭空增加人口。
解聘：今天照付工资，另付一天工资补偿；明天离岗。
照常营业：不增加新安排，已订设备和用工变化仍会生效。
第三场另有：降低工资／提高工资，次日生效，每人1—4枚。

结算的因果顺序
已安排的设备和用工到位 → 价签即时变化、安排下一天措施 → 支付当天开工所需工资/原料/生活费等 → 做面包 → 按价签与钱包交易 → 记剩货、保管和下一天产能。
普通炉3人做6个；快炉2人做12个。缺人、缺炉或缺开工现款，都会限制生产；有炉不等于有人，有产能不等于卖得出。
剩货需要保管，第三天会坏。资金不够可能停炉，但不自动判破产；旧积蓄和已有库存仍可能参与交易。

第一场：恒定的客流数，3天
初始两店各36枚、3名员工、1台普通炉；每天总需求12个，隔壁维持原计划。
目标是三天资金净增最多。买家预算由外部账户提供，没有每个人独立的保留价格。
照常3天：资金57，净增21。当前规则最高：资金87，净增51；提价、再提价、照常是一条最优路线，每天仍卖6个。
所以这场是在特定规则内探索收益，不是在证明现实涨价不会减少销量。

第二场：慢了一拍，5天
重新开账，不承接第一场的87或其他余额。需求按12、20、20、6、12变化，不由玩家选择生成。
玩家选择措施后才看到当日实际客流；界面不会事先公布下一天需求。
价格今天改，购炉与用工明天改。抢到高峰后扩产，可能恰好在低谷承受新增开支；留库存又有保管与变坏的代价。
要观察的是“决定和生效有时差”，不是要求每位玩家都扩产、亏钱或遇到相同库存。
本轮追加优化后，结尾显示本次资金净增、相同规则下照常5天的净增和期末剩货，并回顾实际客流；没有把照常方案冒充最优策略。

第三场：赚钱的算盘，9次经营
移除“需求从哪里来”的追踪页面，新开局从第二场直接进入第三场。
另起新账，本店36枚、尚未营业，不预先结算第一天。现有120枚与对手的既定经营规则保持。
老板的目标是少发工资、多卖产品，让店里留下更多钱。默认只给少发工资／降价抢客／照常营业三个动作；其他原措施放进“其他调整”。
降价当天生效，降工资次日生效。开门前显示预计工资，收摊后显示实付工资、实际卖出和资金变动。
九天结束只显示一次回顾：累计工资、累计卖出、资金净增，并与同样开局、同样对手照常营业比较。
不预设少发工资或降价必定获利；只算已成交销售，剩货不冒充收入。多做、卖出、每个少收和少付工资分别结算。
旧追踪存档可以点击“开始赚钱挑战”，旧账另外保存，前两场记录保留；不伪造两次追踪，也不悄悄改旧账。

第二幕结束与转场
结束时公布的是第一场三天最高收益+51，非三场合计收益；三个实验的账本不能直接累加。
“把镜头拉远：六家店”是可选独立账本，返回后两店对决记录保留。
继续后进入父女对话。三组对话固定讲述“需要面包—没钱—失业—店里卖不掉”的故事，不是本局计算出的特定家庭结局。
本轮已在可见正文标注“独立改编故事，非上一局结算。”；没有恢复此前移除的“展开说明”。
对应代码：public/assets/market-duel/course-game.mjs、course-model.mjs、equipment-model.mjs、steady-challenge.mjs；lib/prologue-state.ts 的 FINISH_BATTLE/NEXT_PAIR/SHOW_STREET_SUMMARY。

第三幕：卖不掉的面包
这幕是只读归纳页，并有一个可跳过的故事判断：需求消失／没钱付款／炉子不够快。每项给一句反馈，不计分、不改经营状态。不会再次扣钱、生产、裁员，也不强制改写上一局库存。
默认呈现：分工/竞争/贸易的效率作用；生产的相互依赖；产权与经营决定权；“按现价卖不掉”和“人人都吃够”的区别。
可选入口：
  换身份，试试谁能作主：厨师可操作烤炉；本演示中排班、投资的最终决定权给老板。只示范权限，不实际购买机器或改变工资。
  韦伯视角：补充组织、核算与规训的解释，不把它冒充上一局利润的计算公式。
  用途与回款：独立例题比较使用价值、交换表现、商品/货币运动与技术；不改主线账本。
  这局的条件及其他资料：查看模型边界和来源，属于补充阅读。
主线按钮“还有什么办法？”进入第四幕。没有要求必须读完所有补充材料。
该幕应得出的是“效率、分配、产权与需求须分开观察”，不能由出现剩货直接推出整个制度必然崩溃。
对应代码：lib/street-summary.js；lib/ownership-permissions.js、weber-perspective.js、value-journey.js。

第四幕：三条出路
当前新开局采用连续经营模式，不限三天或四天，不会到第三天自动降薪、砍单或要求失败。
三张卡分别是增加消费、增加投资、增加出口。每张卡另起自己的账本，再访时保留该卡实际记录；不是依次沿用上一张卡的库存与欠款。
基础规则：商品与设备合并为简化篮子，每份1枚；基础产出50份，家庭购物清单30份，基础工资20枚、生产支出15枚。所有现有账户合计420枚，生产账户初始60枚。

消费卡
选项：加工资／先借钱／照常营业。
加工资：生产账户实际多付工资，再观察家庭购买和生产账户；不是凭空发钱。
先借钱：银行从现有资金放款，下期先还本付息；未还清会暂停新贷款，换招不会抹掉旧债。
照常营业：不加工资、不新借款，但已有债务仍照算。
这卡比较收入和债务对购买能力的不同作用。每次20%的利息是教学设定，不是现实利率；不完整模拟现实银行的存款创造或2008年危机。

投资卡
选项：扩建产线／换掉旧机器／先不添设备。
扩建：设备厂今天收到实际订单，新增产能下一期才能使用，之后也增加维护开支。
换旧机：提高效率、减少部分生产开支，不自动增加产出上限。
先不添：停止追加订单，不撤销已经交付的产能与维护义务。
追加订单来自一笔120枚现款，不每天自动补满。钱用完只说明本局这笔预算用完，不证明现实投资必然失效。

出口卡
选项：押一个大客户／分散找客户／先不接海外单。
大客户：正常条件下订单更集中、开拓开支较低，遇到主动选择的停单条件时可能卖不出去。
分散：多付开拓开支，某些冲击下仍有部分订单；不保证所有条件下都更划算。
先不接：停止本期海外销售，不退回历史运费，也不清除已有剩货。
海外客户同样只有本局120枚现款；未模拟其后续收入、进口和资金回流。不能把有限钱包的耗尽写成“到了某一天出口必然失败”。

三张卡的共同控制
每次选择一项经营措施就结算下一天，资金、库存、欠款与已到设备连续承接；查看账本、改分量或挑选条件不单独结算。
“换个分量”在0—15枚/份间调整，步长5；不操作就不改变账本。
“额外挑战”可选收入变化、设备订单变化或海外订单变化；只影响所选下一天，之后恢复正常条件，既有债务和库存等仍保留。
可看当日/历史账、从头重试并保留旧记录，或返回菜单改选其他路线。
至少观察到一次实际生产和交易后，可返回菜单收下这张卡；不要求出现逆风、亏损或达到固定回合数。
收下1张后可主动选择“先继续故事”；收下3张后可选“继续故事”。只打开卡片不计完成，重开会撤销该卡的完成资格，其他卡不被伪造完成。

实际结算例子（分量10、正常条件；不是现实预测）
加工资：第1、2天生产账户均60，剩货均0，无债务。
先借钱：第1天账户70、剩货0、债务10；第2天账户68、剩货12、债务10。眼前多买，不代表后续相同。
扩建：第1天账户70、剩货0、增加产能10；第2天账户80、剩货8、累计产能20。
换旧机：第1天账户70、剩货0；第2天账户80、剩货2。现金相同也可能对应不同的货和设备结构。
出口：第一天大客户方案账户68、分散方案66，两者都卖出10份海外订单；差别来自实际运输与开拓开支。
对照详情见同目录验收材料中的账目样例。所有数值由当前结算函数生成，不手工改写存档。
